# Native scene wallpaper

[한국어](BACKGROUND.md) · **English**

In **Settings → Wallpaper → Wallpaper Composer**, combine the left and right
images into one scene. Merely selecting files does not change the current
wallpaper.

1. In Source, choose the originals, cover/contain behavior, and focal points.
2. In Layers, define masks with foreground inclusion, background exclusion,
   connected-region fill, and erase. Up to seven layers in addition to the
   background can be added.
3. In Motion, configure layer depth and scene movement.
4. In Preview, inspect motion generated by the actual native shader and save
   a profile for each display.
5. Register the two-sided scene and apply it from the `SUPER+ALT+W` selector.
   The selector can also edit names, ordering, and profiles.

Arrow keys, the wheel, arrows, and side cards navigate scenes in the selector.
Enter, Apply, or clicking the center card requests a transition. Escape and an
outside click close it. The first design uses three fixed slots, a center pair
card, per-monitor palettes, and the existing Shell glow/motion path. Spacing,
size, and speed should be adjusted after inspecting the real display.

## Build and validation

Native dependencies are C11, wayland-client/wayland-egl, EGL/GLES2, libpng,
libjpeg, json-c, wayland-scanner, and wayland-protocols. The existing
GTK4/gtk4-layer-shell Shell dependencies are also required.

OpenCV is needed only by the offline profile-production worker.
`requirements-background.txt` pins the validated OpenCV version. The native
wallpaper playback process does not load Python or OpenCV. No AI model, model
download, or Cubism SDK is used.

```sh
python3 -m venv --system-site-packages /path/to/profile-runtime
/path/to/profile-runtime/bin/python -m pip install -r requirements-background.txt
LUMINOPHORE_PROFILE_PYTHON=/path/to/profile-runtime/bin/python scripts/verify-background-scene /path/to/new-candidate
```

The verification script copies the Shell source and native executable into the
same candidate and runs the complete test suite plus offscreen EGL pixel
validation. The candidate `manifest.json` contains every file hash and the
renderer build ID. It does not replace the existing runtime.

To inspect the candidate Settings UI, run
`shell/luminophore-shell settings --page wallpaper` from that candidate and
point `LUMINOPHORE_PROFILE_PYTHON` at the prepared production environment.
Actual application must happen only after activating the matching Shell daemon
and native binary together. This verification script does not install anything,
restart services, or restart the session.

## Contracts and limits

- Scene/Profile/Package/IPC schema 1. The package compiler identity is
  `opencv-<version>/luminophore-profile-2`. Outputs are distinguished by
  original hash, draft, and compiler identity.
- PNG/JPEG originals: up to 8 million pixels for authoring input and 32 million
  pixels for native static input. EXIF orientation is normalized while producing
  profiles. JPEGs in directly authored static scenes use the original pixel
  orientation.
- Up to eight RGBA layers and 128 MiB of decoded texture data per profile.
  Current+next textures across two outputs are limited to 512 MiB and composite
  targets to 256 MiB. GL limits are checked during preparation.
- 16×16 grid and movement up to 0.05. Layer order is bottom → top. The base
  background depth is fixed at 0.
- Up to 10,000 strokes per mask layer. Worker CPU limit 90 seconds, address
  space 4 GiB, compile response limit 100 seconds, preview generation limit
  30 seconds. Native preview is a looping sample at 640×360 with at most
  48 frames / 12 fps and is not a measurement of real desktop frame pacing.
- Additional compilation is refused once stored profile outputs exceed 2 GiB.
  Stored originals/packages are not deleted automatically. Temporary
  compile/preview requests clean up only files owned by that request.
- Thumbnail cache: up to 24 items at 320×200, one worker, up to 12 pending
  assets. Drag autosave uses a 500 ms debounce; source preview decoding uses a
  separate worker.
- Scene list: up to 1,000 entries, history 64, one latest pending request.
  PREPARE/READY uses a shared monotonic start time; the current scene and palette
  are updated only after final presentation feedback from both outputs. Different
  vblanks themselves are not synchronized.
- Initial role binding supports exactly two outputs at different x positions.
  Unsupported layouts are explicitly rejected.

## Ownership and recovery

`BackgroundSceneController` is the sole apply owner. Settings edits drafts and
saved scenes; IPC carries scene intent. The scene list is stored at
`$XDG_CONFIG_HOME/luminophore-shell/wallpaper-scenes.json`; profiles and
last-good state live under `$XDG_STATE_HOME/luminophore-shell`.

Preparation failure leaves the existing native display intact. Process loss,
timeouts, or topology changes after commit re-prepare from the last-good
snapshot. After three failures, the system uses a native solid-color recovery
screen and degraded state and does not automatically start an external provider.
A compiled last-good scene can recover from retained layers even if the original
source is gone. New applies reject changed or missing originals.

Existing same-user hyprpaper/awww-daemon processes are stopped only after both
outputs present the first explicitly applied scene. On later starts where native
state exists, autostart does not launch an external provider. Before the first
native activation, existing autostart behavior is preserved. If an external
systemd provider service has been registered separately, its restart policy must
also be removed during deployment.

Manual development rollback is a separate operating procedure: stop the Shell,
preserve the last-good state **without deleting it**, and restore the previous
Shell/provider. This differs from the product runtime fallback. Originals and
the scene library remain intact. Greeter/login paths are not modified.

## Still needs a real session

Real-hardware validation is still required for dual presentation on Wayland,
hotplug/kill recovery, per-monitor scale/crop/seams, black-frame behavior,
keyboard/outside-click/input-empty behavior, 60/144 Hz frame pacing, mask/fill
quality on user originals, and design acceptance. Passing offscreen EGL and
fixtures does not mark these items complete.
